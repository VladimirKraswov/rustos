# Инструкции для coding-агентов RustOS

Этот файл действует во всём репозитории. Перед изменением файла также прочитай
ближайший к нему `AGENTS.md`: локальные правила уточняют, но не отменяют эти.

## Сначала установи факты

1. Выполни `git status --short --branch`. Не исправляй, не форматируй и не
   включай в коммит чужие изменения.
2. Прочитай документ подсистемы из `docs/` и публичные типы, которые реально
   использует код. Документ с планом не доказывает, что функция реализована.
3. Найди существующий аналог через `rg`; продолжай один принятый паттерн,
   вместо создания параллельного framework.
4. Для небольшой задачи меняй одну подсистему и минимально необходимый adapter.
   Не совмещай в одном change новый ABI, драйвер, сервис и приложение.

Карта репозитория и готовые наборы проверок находятся в
[`docs/AGENT_WORKFLOW.md`](docs/AGENT_WORKFLOW.md). Архитектурная правда — в
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), честный статус self-hosting — в
[`docs/SELF_HOSTING.md`](docs/SELF_HOSTING.md).

## Неподвижные границы

- RustOS — микроядерная система. Новая политика, парсер формата, файловая
  система, GUI runtime или драйвер не должны незаметно разрастаться в kernel.
  Bootstrap-код в kernel допускается только как явно названный переходный слой.
- Обычное приложение не обращается к портам, MMIO, framebuffer, page tables или
  физическим кадрам. Оно использует typed API, DLL facade и capabilities.
- Межпроцессные и DLL-границы не экспортируют Rust ABI. Используй `extern "C"`,
  `#[repr(C)]`, целые фиксированной ширины, offsets/handles и явное владение.
- Указатели одного процесса не передаются другому. Большие данные идут через
  bounded shared memory, управляющие сообщения — через capability IPC.
- Ошибка user process или service должна завершить/перезапустить виновника, а
  не вызвать panic kernel. Все длины, индексы, offsets и capacity проверяются.
- ISA-зависимый код живёт только в архитектурной границе. Переносимый код обязан
  собираться для AMD64 и AArch64; новые inline/global asm вне неё запрещены.
- Kernel и ранние `no_std` crates не получают скрытый heap. Если подсистема
  использует const-generic budgets, переполнение возвращает ошибку без
  публикации частичного состояния.

## Код учебной системы

- Имена в коде — ясные английские; содержательные комментарии и документация —
  на русском. Комментарий объясняет причину, invariant, ownership или аппаратное
  ограничение, а не повторяет строку кода.
- `unsafe` минимален и сопровождается `// SAFETY:` с проверяемым основанием.
- Не подавляй ошибку через произвольный fallback. Bounded degradation допустима,
  если она является частью контракта и тестируется.
- Не добавляй зависимости без необходимости. Версии workspace фиксируются
  точно; `std`/heap/host API нельзя протащить в `no_std` код транзитивно.
- Не меняй публичный ABI или on-disk format без версии, обратной совместимости
  либо миграции и негативных тестов.

## Минимальная единица работы

Хорошая задача для небольшого агента имеет один наблюдаемый результат, обычно
до нескольких тесно связанных файлов. В отчёте должны быть:

1. что изменено и какая граница намеренно не затронута;
2. какие проверки выполнены дословно и их результат;
3. какие ограничения остались;
4. список изменённых файлов из `git diff --name-only`.

Не объявляй готовыми ring 3, GPU acceleration, self-hosting или persistence,
если проверка подтверждает только kernel bootstrap, CPU backend или RAM state.

## Базовые проверки

Всегда запускай `cargo fmt --all -- --check`. Затем выбери самый узкий набор из
`docs/AGENT_WORKFLOW.md`. Для изменения общей переносимой границы обязательны
`make test-arch`; для видимого desktop/terminal поведения — `make test-gui`.
Полный `make test` нужен для ABI, lifecycle, loader, VFS или нескольких слоёв.

Не запускай `make clean`, destructive git-команды и массовое автоформатирование
чужих файлов. Не коммить и не push без прямого задания владельца репозитория.
